# SDK Overview

LedgerDB does not ship a network server. There is no daemon to point a driver at, no TCP listener to negotiate, no on-wire protocol of its own. The whole database is a git repository on a local filesystem plus an optional SQLite sidecar that materialises the current state of each collection from that repository. Everything a caller does — write a document, read it back, query it, watch the index, verify integrity — is a synchronous operation against those two stores. There is no "client" in the request/response sense; there is only code that calls into those stores, and the SDK section of this wiki describes the three ways that calling happens.

The three surfaces are the `ledgerdb` CLI, the Go SDK in `pkg/ledgerdbsdk/`, and the TypeScript SDK in `packages/sdk-typescript/`. All three are exposed by the same single binary or by the same single Go module, and all three are built on top of the same `internal/app/*` application services that the CLI commands invoke. The difference between them is not what they can do — they can all do the same things — but how the caller wants the work to be packaged: a process you spawn, a Go package you import, or a Node module that spawns the process for you.

The phrase "smart client" appears in the project README. It means: the client is the database. There is no remote query planner deciding what an indexed read costs; there is a local SQLite file that the caller opened directly, and the planner is `EXPLAIN QUERY PLAN` running in the same process. There is no remote write-coordination protocol resolving a quorum; there is a git commit that the caller's own process produced, and synchronisation with other replicas is a `git fetch` followed by a `git push` against `origin`. Every surface described here upholds that contract by composing the same internal services in the same address space — or, in the CLI bridge case, by spawning a process that does so.

## The three surfaces

The `ledgerdb` CLI is the canonical surface. It is implemented in `internal/cli/`, wired together in [`internal/cli/root.go`](../tree/main/internal/cli/root.go), and exposes every documented operation as a `cobra` subcommand under `internal/cli/commands.go` and its sibling `cmd_*.go` files. Every other surface is a wrapper around this one. The CLI is the right choice for shell scripts, for CI pipelines, for one-off operations from an operator's seat, and for the interactive REPL described on [SDK REPL And Query Explain](SDK-REPL-And-Query-Explain). Detailed coverage of every command lives on [SDK CLI Reference](SDK-CLI-Reference).

The Go SDK in `pkg/ledgerdbsdk/` is the in-process surface. It is the one to use when LedgerDB is embedded into a larger Go program that needs document storage with history — a desktop app, a single-node service, a CLI tool that wants `Get`/`Put`/`Query` without shelling out. It opens the git store and the SQLite index directly through [`Client.Open`](../tree/main/pkg/ledgerdbsdk/client.go), runs every operation in the caller's goroutine, and returns Go values. There is no spawn, no IPC, no serialisation overhead. The full surface — config, lifecycle, query routing, watch lifecycle — is documented on [SDK Go SDK](SDK-Go-SDK).

The TypeScript SDK in `packages/sdk-typescript/` is the CLI-bridge surface. It exists because Node processes do not link Go libraries cleanly, and because the LedgerDB team chose to keep the TS package free of native bindings. [`LedgerDBClient`](../tree/main/packages/sdk-typescript/src/client.ts) wraps each operation in a `child_process.execFile` call to the `ledgerdb` binary, parses the JSON output, and returns a Promise. The npm package's `postinstall` script (`packages/sdk-typescript/scripts/postinstall.js`, and the smaller standalone [`npm/ledgerdb/`](../tree/main/npm/ledgerdb) wrapper) downloads the right prebuilt binary for the host platform. It is the right surface for a Node service that already has a process model and can tolerate the ~10ms spawn cost per call. Detail lives on [SDK TypeScript SDK](SDK-TypeScript-SDK).

A fourth surface, the lower-level core package at `pkg/ledgerdb/`, is mentioned here for completeness. It is two files — `pkg/ledgerdb/doc.go` and `pkg/ledgerdb/execute.go` — and its current public API is exactly one function, `Execute()`, which forwards to `internal/cli.Execute()`. Its real purpose is to support `-buildmode=archive` and `-buildmode=shared` builds (see the `build-core` target in the [`Makefile`](../tree/main/Makefile)) so the CLI binary can be statically or dynamically linked from another Go program. It is not the embedder's API; that is `pkg/ledgerdbsdk/`.

## What each surface upholds

The three surfaces inherit the same operational guarantees because they all funnel into the same `internal/app/*` services. A `doc put` from the CLI calls `docapp.NewPutService(...).Put(...)` in `internal/cli/commands.go`. A `Client.Put` from the Go SDK calls the same constructor with the same dependencies in `pkg/ledgerdbsdk/doc.go`. A `client.put(...)` from TypeScript spawns the CLI and ends up at the same line. The result of each path is a git commit with the same shape, written by the same `gitrepo.Store`, governed by the same `HistoryMode` (append or amend) loaded from the repository's `db.yaml` manifest.

That convergence has one consequence worth flagging. Because every surface ultimately runs a `git` operation against the local repository, two processes that write to the same repo at the same time will race for the lock that `git` itself maintains in `.git/index.lock`. The Go SDK serialises within a single `Client` because its operations run sequentially in the caller's goroutine and it holds no extra coordination of its own; but if the caller spawns two clients against the same repo, or runs the CLI from two shells at once, the second one will see the standard git "another git process seems to be running" error. The right pattern is one writer per repository, and the SDK pages spell that out where it matters.

The second consequence is that the surfaces are honest about what they cannot do. There is no streaming subscription, no long-poll, no server-sent events. The single long-lived operation in the entire system is `ledgerdb index watch`, and it is implemented as a polling loop in `internal/cli/commands.go` that calls `service.Sync(...)` on an interval. The Go SDK exposes the same loop as `Client.StartIndexWatch` in `pkg/ledgerdbsdk/index.go`. The TypeScript SDK exposes it as `LedgerDBClient.startIndexWatch`, which spawns `ledgerdb index watch` and returns the `ChildProcess` handle. Three surfaces, one loop, no protocol.

## Who each is for

The CLI is for operators, for scripts, and for any caller whose workflow already lives in a shell. It is the only surface that exposes every flag — `--repo`, `--json`, `--log-level`, `--sign`, `--sync`, the index `--metrics-addr` and `--audit-log` recently added in commit `7179d14` — and it is the surface the README's examples target. Anything described on the README's CLI quick-start can be run verbatim against a freshly built binary.

The Go SDK is for embedders. A program that imports `pkg/ledgerdbsdk` gets typed return values (`PutResult`, `Doc`, `LogEntry`, `IndexSyncResult`), a sentinel error set (`ErrNotFound`, `ErrManifestMismatch`, `ErrInvalidCursor` in `pkg/ledgerdbsdk/errors.go`), a `*sql.DB` handle for direct SQL on the index, and a `context.Context`-driven lifecycle. It does not get a shell. It is the right choice when LedgerDB is part of the program and not a tool the program calls.

The TypeScript SDK is for Node services that want LedgerDB without writing Go. The tradeoff is the process spawn per call — `execFile("ledgerdb", ...)` for every `put`, `get`, and `patch` — versus the simplicity of a one-line npm install and the absence of any native module. For request-rate workloads where the spawn cost dominates, callers should prefer running the CLI's REPL (see [SDK REPL And Query Explain](SDK-REPL-And-Query-Explain)) inside a persistent child process, or move to the Go SDK; the TS SDK is honest about this tradeoff on its own page.

## What the SDK is not

It is worth being explicit about what is intentionally absent because the absences shape the integration boundary. There is no network protocol of LedgerDB's own — no gRPC service, no JSON-RPC endpoint, no Postgres wire compatibility, no HTTP API the SDKs talk to. If a workload wants remote access to a repository, it does so through `git` itself over SSH or HTTPS, and the SDK runs against a local clone. There is no connection pool, no auth handshake, no retry loop with exponential backoff, because there is no network call to retry.

There is no concurrent-writer protocol. Two callers writing to the same repository at the same time will collide on the git index lock, and one will fail. Callers needing multi-writer coordination either serialise through a single in-process `Client`, or push writes through a leader-elected single instance, or partition by repository. The SDK does not pretend that pessimistic locking turns into optimistic concurrency for free.

There is no streaming subscription. `index watch` polls; the channel returned by `Client.WatchResults()` emits at the configured interval; the TypeScript SDK forwards the same polled output through a child process's stdout. A caller that needs sub-second change notification has to set the poll interval accordingly and pay the resulting fetch cost. There is no push.

There is no remote query planning. The query path runs in the caller's process against the local SQLite sidecar, and `EXPLAIN QUERY PLAN` (covered on [SDK REPL And Query Explain](SDK-REPL-And-Query-Explain)) is the only planning surface. Indexes are defined per collection at `collection apply` time and materialised at sync time; that is the whole indexing story.

## Reading order

Read [SDK CLI Reference](SDK-CLI-Reference) first if you want to understand the command surface — every page below it refers back to specific commands. Read [SDK Go SDK](SDK-Go-SDK) if you are embedding LedgerDB; the worked example there shows the open-write-query-close cycle. Read [SDK TypeScript SDK](SDK-TypeScript-SDK) if you are wiring LedgerDB into a Node stack and need to understand the postinstall behaviour and the bridge cost. Read [SDK REPL And Query Explain](SDK-REPL-And-Query-Explain) last; it is two operator tools that round out the CLI surface and are easier to motivate after the rest of the section.
