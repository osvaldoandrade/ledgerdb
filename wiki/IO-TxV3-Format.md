# IO TxV3 Format

Every write LedgerDB accepts is encoded as a `TxV3` protobuf message and stored as a git blob. The encoding is the durable record. The SQLite sidecar can be deleted and rebuilt; the `state/` tree can be regenerated by replaying the log; only the TxV3 blobs are the source of truth. This page is the field-by-field reference for that format, the codec that produces it, and the canonical JSON requirement that makes the resulting bytes reproducible across machines.

The message is defined once, in `internal/infra/txv3/tx.proto`, and compiled into Go at `internal/infra/txv3/tx.pb.go`. The codec — encode and decode — lives in `internal/infra/txv3/codec.go`. There is exactly one wire schema; there is no version negotiation in the protobuf itself. The version is encoded in the package name (`ledgerdb.v3`) and in the file extension (`.txpb`). A `v4` would be a separate package with a separate file extension and a separate decoder.

## The protobuf schema

The schema is small enough to inline. From `internal/infra/txv3/tx.proto`:

```protobuf
syntax = "proto3";
package ledgerdb.v3;

message Transaction {
  string tx_id = 1;
  int64  timestamp = 2;
  string collection = 3;
  string doc_id = 4;

  enum Op {
    UNKNOWN = 0;
    PUT     = 1;
    PATCH   = 2;
    DELETE  = 3;
    MERGE   = 4;
  }
  Op op = 5;

  oneof payload {
    bytes snapshot = 6;
    bytes patch    = 7;
  }

  string parent_hash = 8;
  string schema_version = 9;
}
```

Field by field:

- `tx_id` (1) — a ULID generated by `internal/infra/ident/ulid.go:19-25`. ULIDs are time-ordered, so sorting transactions by `tx_id` yields the same order as sorting by `timestamp` modulo ties. The ULID is the stable identifier the truncate threshold compares against (`internal/app/dr/truncate.go:280-285`).
- `timestamp` (2) — unix-nanos UTC at the moment the write was constructed by the producer. The git commit's author/committer date is set from the same clock at `internal/infra/gitrepo/tx_store.go:414`. The two are independent; the protobuf field is the canonical one for replay and ordering.
- `collection` (3) — the logical collection name (e.g. `users`). Used to derive the on-disk path via `domain.StreamPath` (`internal/domain/hds.go:21-30`) and to scope the SQLite table.
- `doc_id` (4) — the per-collection document identifier. Combined with `collection` it produces the HDS hash `sha256(collection + "/" + doc_id)` (`internal/domain/hds.go:15-19`) that anchors the document's path on disk.
- `op` (5) — one of `PUT` (replace snapshot), `PATCH` (JSON Patch applied to current snapshot), `DELETE` (tombstone), or `MERGE` (apply patch when present, otherwise upsert snapshot). The validation matrix is in `Transaction.Validate` at `internal/domain/tx.go:57-96`: `PUT` requires `snapshot`, `PATCH` requires `patch`, `DELETE` forbids both, `MERGE` requires at least one.
- `payload` (6/7) — a `oneof` carrying either a JSON snapshot or a JSON Patch (RFC 6902). Both are `bytes` because the protobuf does not parse the contents; the canonicalisation step (below) does.
- `parent_hash` (8) — the SHA-256 of the previous transaction blob on this document's stream. The first write on a stream has `parent_hash == ""`. The CAS loop at `internal/infra/gitrepo/tx_store.go:153-157` rejects writes whose `parent_hash` does not match the current head, which is how concurrent writers serialise.
- `schema_version` (9) — an opaque application-defined string. LedgerDB does not interpret it; the sidecar stores it verbatim alongside the document (`internal/infra/sqliteindex/store.go:430-447`). Schema-aware consumers can read it to drive migrations.

The `UNKNOWN = 0` op is reserved as the proto3 default. `codec.go:96-107` returns `invalid tx op` on attempts to encode it, and `fromProtoOp` returns the same on decode. There is no path through which an `UNKNOWN` blob can be written by the system; the validation runs before encoding.

## The deterministic codec

The encode side is six lines:

```go
func Encode(tx domain.Transaction) ([]byte, error) {
    if err := tx.Validate(); err != nil {
        return nil, err
    }
    pb, err := toProto(tx)
    if err != nil {
        return nil, err
    }
    return proto.MarshalOptions{Deterministic: true}.Marshal(pb)
}
```

The `Deterministic: true` flag is load-bearing. Without it, protobuf's wire format is not stable across encodings — map fields can be ordered arbitrarily, and unknown fields can be re-ordered relative to known ones. With it, the same `domain.Transaction` produces the same bytes every time, on every machine, with every supported Go version. This is what lets the SHA-256 of the encoded blob be used as a content-addressable identifier across a distributed system.

The TxV3 message itself has no map fields, so the determinism guarantee comes mostly for free in practice. The flag is still set because future schema evolution might add maps, and because the determinism contract is part of the format, not an emergent property of the current shape.

Decode is the inverse. `Decode` (`codec.go:35-42`) accepts arbitrary bytes, calls `proto.Unmarshal`, then runs `fromProto` to convert back to a `domain.Transaction`. The validation that happens on encode does not happen on decode — a malformed-but-parseable blob round-trips. This is intentional: the indexer at `internal/app/index/service.go:283-303` decodes every historical blob and then calls `Validate` explicitly, so corruption surfaces at the application boundary rather than inside the decoder.

## Canonical JSON for the payload

The `snapshot` and `patch` fields are `bytes`, not nested protobuf messages, because LedgerDB carries JSON inside them and JSON has no canonical protobuf representation. The canonical form is computed before the bytes hit the protobuf. The canonicaliser at `internal/infra/canonicaljson/canonicalizer.go:12-23` wraps `github.com/go-json-experiment/json`'s `jsontext.Value.Canonicalize`, which implements the RFC 8785 canonical-form rules: sort object keys lexicographically, strip insignificant whitespace, normalise numeric representations.

The reason this matters is content addressing. Two producers that submit `{"a":1,"b":2}` and `{"b":2,"a":1}` describe the same document. Without canonicalisation they would produce different snapshot bytes, different TxV3 blobs, and different SHA-256 hashes — so the parent-hash chain would diverge across machines for the same logical write. With canonicalisation, the snapshot bytes are byte-identical and the chain is reproducible.

The canonicaliser is invoked at the indexing boundary in `internal/app/index/service.go:321-322` before the payload is stored in the sidecar, and is expected to be invoked by the SDK before the transaction is submitted. The codec itself does not canonicalise — it trusts the caller — because re-canonicalising on every read would be wasteful and would make the protobuf bytes not actually content-addressed. The contract is: producers canonicalise once, when constructing the transaction, and the bytes do not change after that.

## The hash

The SHA-256 of the encoded blob is the transaction hash. The implementation is the standard library at `internal/infra/hash/sha256.go:10-13`:

```go
func (SHA256) SumHex(data []byte) string {
    sum := sha256.Sum256(data)
    return hex.EncodeToString(sum[:])
}
```

This hash is what `parent_hash` references, what the sidecar stores in the `tx_hash` column, what the integrity verifier checks, and what `truncate` uses to record which blobs are being kept. The hash is **not** the git blob's SHA-1 object hash. Git computes its own object hash over `blob <size>\0<content>`; LedgerDB computes its hash over the content alone, with SHA-256. Both hashes coexist — the git one identifies the object in the git store, the LedgerDB one identifies the transaction in the protocol — and neither is derivable from the other without re-reading the blob.

## On-disk layout of one blob

Inside the bare repository, a transaction blob is stored as a regular git blob object. The filename used to enter the blob into the tree is constructed by `txFileName` at `internal/infra/gitrepo/tx_store.go:493-506`:

```
<timestamp>_<op>.txpb
```

For example, `1717612345678901234_put.txpb`. The timestamp prefix makes `git ls-tree` output naturally chronological inside a stream's `tx/` directory. The `.txpb` suffix (declared at `internal/domain/storage.go:6`) is the marker the `index_source.isTxPath` filter at `internal/infra/gitrepo/index_source.go:385-387` uses to skip non-tx files (like the `HEAD` pointer) when walking a tree.

Under the `amend` history mode (`internal/domain/config.go:42-46`), the filename is overridden to the constant `current.txpb` (`internal/domain/storage.go:7`) and every write overwrites the previous blob's tree entry. This collapses history and is the same filename the `state/` tree uses; the [IO-State-Tree](IO-State-Tree) page covers that mirror.

## Decoding a blob with stock tools

The fact that the blobs are plain protobuf inside plain git makes them readable without LedgerDB. Given the path to a bare repo and a tx blob hash from `git log`, the operator can dump the protobuf wire form:

```
$ git -C /path/to/repo cat-file blob <blob-sha1> > tx.bin
$ protoc --decode=ledgerdb.v3.Transaction \
         --proto_path=internal/infra/txv3 tx.proto < tx.bin
tx_id: "01HVZ..."
timestamp: 1717612345678901234
collection: "users"
doc_id: "user-42"
op: PUT
snapshot: "{\"email\":\"x@y.z\",\"name\":\"X\"}"
parent_hash: "9f86d0..."
schema_version: "v1"
```

Or in Go, three lines using the same package the codec uses:

```go
data, _ := os.ReadFile("tx.bin")
tx, _ := txv3.Decode(data)
fmt.Printf("%+v\n", tx)
```

The recovery story rides on this. If every other piece of LedgerDB is gone — the SQLite sidecar, the `state/` tree, the application binaries — the protobuf message is self-describing enough that a future operator can walk the commit history with `git`, decode every blob with `protoc`, and reconstruct the document model.

## Validation

`Transaction.Validate` (`internal/domain/tx.go:57-96`) is the only place that enforces the field invariants. The checks are:

- `tx_id` non-empty.
- `timestamp` non-zero.
- `collection` non-empty.
- `doc_id` non-empty.
- `op` is one of the four valid ops (not `UNKNOWN`).
- `snapshot` and `patch` are not both set.
- Per-op payload presence: `PUT` requires `snapshot`, `PATCH` requires `patch`, `DELETE` forbids both, `MERGE` requires at least one.

The encoder calls `Validate` before marshalling. The indexer calls it after decoding (`internal/app/index/service.go:290-292`). The integrity verifier calls it on every blob it walks. This is the single boundary between "any bytes that parse as protobuf" and "a transaction LedgerDB will replay".
